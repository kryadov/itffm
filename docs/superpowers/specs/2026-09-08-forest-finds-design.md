# Лесные находки за пределами грибов — дизайн-документ

Дата: 2026-09-08
Статус: одобрен, в реализации.
Расширяет: `docs/superpowers/specs/2026-09-07-mushroom-game-design.md`.

## 0. Зачем

Игра сейчас — только про грибы. В реальном лесу собирают не только их: ягоды,
травы, орехи, а иногда просто находят что-то стоящее внимания — птичье гнездо,
сброшенный рог, необычный камень. Расширение добавляет эти категории в ту же
игру, той же механикой, без второй игры внутри игры.

## 1. Решения брейншторма

| Решение | Почему |
|---|---|
| Одна энциклопедия на все виды, фильтр по типу объекта (`kind`) | Игрок не переключается между «игрой в грибы» и «игрой в ягоды» — это один лес, один список того, что в нём нашлось. |
| `kind: 'mushroom' \| 'berry' \| 'herb' \| 'nut' \| 'find'` — дискриминатор в общей `Species` | Одна схема, один загрузчик, одна энциклопедия — расширение поля, а не второй параллельный конвейер. |
| Полноценная процедурная морфология на вид, для каждого `kind`, как у грибов | Проект целиком построен на «данные вида — источник правды для модели» (см. §4.1 основной спеки); упрощённые «один генератор на тип» модели предали бы эту идею ровно там, где она успела прижиться. |
| `ecology/sites.ts` и `ecology/spawn.ts` не меняются | Обе смотрят только на `species.ecology` (substrate/biomes/season/moisture/mycorrhizal/frequency/gregarious) и никогда — на morphology. Новый `kind` проходит тот же конвейер бесплатно, если его данные вида просто заполняют те же поля. |
| `edibility` становится необязательным полем | У находки (`kind: 'find'`) съедобности нет и не может быть — не «несъедобно», а вопрос неприменим. |
| Три действия («В корзину» / «Срезать» / «Оставить расти») одинаковы для всех `kind` | Не решать за игрока в UI, что означает «срезать» ягоду или гнездо — читается как «взять руками» независимо от типа, текст кнопок можно оставить как есть. |
| Один общий span учёта (`save/store.ts`'s `finds`/`discovered`) на все `kind` | Уже ключуется по `speciesId`, независимо от типа — менять нечего. |

### Сознательная неточность языка

`ecology.substrate: 'soil'` для камня или `ecology.mycorrhizal: []` для гнезда —
метафора, натянутая на нерастущий объект ради переиспользования одной системы
подсчёта. Это принятый компромисс, а не недосмотр: две параллельные системы
разбора «выросло» и «нашлось» стоили бы дороже, чем одно поле с чуть
неточным именем.

## 2. Архитектура

### 2.1 Схема (`species/schema.ts`)

`Species` — размеченное объединение по `kind`. Общие поля (`id`, `gbifKey`,
`name`, `lookalikes`, `ecology`, `text`, `media`) остаются как есть;
`edibility` становится `edibility?: Edibility`; `morphology` типизируется по
`kind`:

```ts
export type Species =
  | (SpeciesCommon & { kind: 'mushroom'; morphology: MushroomMorphology; edibility: Edibility })
  | (SpeciesCommon & { kind: 'berry'; morphology: BerryMorphology; edibility: Edibility })
  | (SpeciesCommon & { kind: 'herb'; morphology: HerbMorphology; edibility: Edibility })
  | (SpeciesCommon & { kind: 'nut'; morphology: NutMorphology; edibility: Edibility })
  | (SpeciesCommon & { kind: 'find'; morphology: FindMorphology })
```

Ручная валидация (как сейчас, без библиотеки — данные пишут люди, ошибка должна
называть файл и поле) разбирается по `kind` в начале, дальше — та же схема
"по полю с понятной ошибкой", что и сейчас для `morphology.cap` и других.

### 2.2 Модули по типу

Мышью — `mushroom/` уже есть. Симметрично:

```
src/berry/{schema.ts?, build.ts}
src/herb/build.ts
src/nut/build.ts
src/find/build.ts
```

(`schema.ts` для конкретного типа нужен, только если его морфология сложнее
пары примитивов — решается по месту при реализации каждого типа, не заранее.)

Каждый экспортирует:
- `buildX(morphology, seed, age): THREE.Group` — подробная модель для осмотра/энциклопедии.
- `toWorldMesh(group): THREE.Mesh` — тот же приём, что и у грибов: один меш с
  вершинными цветами для мира, чтобы сотни ягодных кустов не стоили сотен
  вызовов отрисовки.
- `traitsFor(species): { label: string; value: string }[]` — короткий список
  признаков для карточки осмотра, свой на каждый тип (у гриба — шляпка/ножка/
  гименофор, у ягоды — размер и цвет кисти, у находки — материал и размер).

### 2.3 Диспетчер по `kind`

`game/scene.ts` (сборка мира) и `ui/inspect.ts` (3D-превью) сейчас вызывают
`buildMushroom`/`toWorldMesh` напрямую. Оба получают один общий диспетчер:

```ts
// src/collectible/build.ts
export function buildCollectible(species: Species, seed: number, age: number): THREE.Group {
  switch (species.kind) {
    case 'mushroom': return buildMushroom(species.morphology, seed, age)
    case 'berry': return buildBerry(species.morphology, seed, age)
    // ...
  }
}
export function collectibleWorldMesh(group: THREE.Group): THREE.Mesh { /* toWorldMesh, общий */ }
```

### 2.4 Энциклопедия

`ui/encyclopediaFilters.ts` получает пятый фильтр `kind?: Species['kind']`
рядом с biome/edibility/hymenium/season. `hymenium`-фильтр остаётся
специфичным для гриба — на не-грибах он просто не совпадёт ни с чем,
это уже поведение `matchesFilters` без изменений. Карточка (`BIOME_LABEL` и
соседние словари в `ui/encyclopedia.ts`) добавляет `KIND_LABEL` для подписи и
иконки типа.

### 2.5 Что НЕ меняется

`ecology/sites.ts`, `ecology/spawn.ts`, `save/store.ts`, `game/pick.ts`,
логика «Срезать»/«В корзину»/«Оставить расти» в `main.ts` — все уже работают
только через `Species`/`Placement`/`speciesId`, ни разу не заглядывая в
`morphology`. Это главный вывод раздела архитектуры: расширение почти целиком
укладывается в существующие точки расширения, не требуя переписывать
работающий код.

## 3. Начальный список видов (v1)

Не исчерпывающий — база расширяется тем же способом, что и с 3 до 31 гриба.
Для старта — по 3-4 вида на категорию, каждый с настоящей экологией и текстом
на двух языках, как сейчас у грибов:

- **Ягоды**: черника (*Vaccinium myrtillus*), брусника (*Vaccinium
  vitis-idaea*), морошка (*Rubus chamaemorus* — верховое болото, единственная
  ягода штучно совпадающая с биомом `wetland`), земляника лесная (*Fragaria
  vesca*).
- **Травы**: крапива двудомная (*Urtica dioica*), черемша (*Allium ursinum*),
  щавель кислый (*Rumex acetosa*).
- **Орехи и семена**: лещина обыкновенная (*Corylus avellana*), шишка
  (условный вид — не ботанический таксон, обсудить при реализации: возможно,
  это не отдельный вид, а деталь дерева соответствующего рода), жёлудь дуба
  (*Quercus robur*).
- **Находки**: птичье гнездо, сброшенный рог (косули/оленя, по биому),
  перо, «интересный камень» — последние три, вероятно, не имеют
  биологического вида в строгом смысле и получат вымышленный, но
  правдоподобный `id`/`name` вместо `gbifKey` (поле уже необязательно
  по некоторым видам? — уточнить на `species/schema.ts` при реализации:
  скорее всего `gbifKey` тоже становится необязательным для `kind: 'find'`).

## 4. Тестирование

Каждый новый модуль — тот же ритм, что и `mushroom/build.test.ts`:
детерминизм по seed, отсутствие «химерных» пропорций, разумные границы
размеров. `species/schema.test.ts` получает тесты на валидацию каждого
`kind` (включая отказ схемы принять `edibility` там, где морфология
`find`, если это будет запрещено явно, — или разрешение отсутствия поля).
`ui/encyclopediaFilters.test.ts` получает тесты на новый `kind`-фильтр.

## 5. Порядок реализации

Один вид за проход, не всё сразу, несмотря на то, что спека — одна большая:
1. Схема: `kind`-дискриминатор, `edibility?`, общий `SpeciesCommon`.
2. Первый тип целиком (ягоды: схема морфологии → генератор → 2-3 вида данных
   → диспетчер → фильтр в энциклопедии → визуальная проверка).
3. Травы, орехи, находки — тем же шаблоном, по одному коммиту на тип.

Так каждый шаг остаётся тестируемым и обозримым, даже если по бумаге это одна
спека, а не четыре отдельных.
