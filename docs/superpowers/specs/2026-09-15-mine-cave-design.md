# Mine as a real cave — design

Дата: 2026-09-15. Автор дизайна: обсуждение с пользователем + Claude.

## 0. Зачем

Штольня (`src/world/mine.ts`) сейчас — один прямой прямоугольный коридор
длиной 6м, единственная развилка — её нет. Бриллиант лежит в фиксированной
точке у задней стены. Пользователь хочет, чтобы это читалось как настоящая
пещера: спуск под землю у входа, несимметричный вид устья, небольшая система
ходов с тупиками, в которой бриллиант правда нужно искать, и чтобы сам
бриллиант при свете лампы игрока заметно светился и не был идеально
симметричным восьмигранником.

Это не влияет на дизайн-документ игры в целом (`docs/superpowers/specs/2026-09-07-mushroom-game-design.md`)
и на пятый предмет квеста (`docs/superpowers/specs/2026-09-13-quest-items-design.md`) — только на
то, как устроена штольня внутри и как выглядит один из пяти предметов.

## 1. Модель ходов — граф сегментов

`Mine` перестаёт хранить один `heading` как единственное направление бурения;
вместо этого хранит дерево сегментов, сгенерированное детерминированно из
мирового `seed` через `mulberry32`, тем же способом, что и остальной
процедурный контент проекта.

```ts
interface MineSegment {
  id: number
  parentId: number | null      // null — корневой (входной) сегмент
  x0: number; z0: number       // начало, в локальных метрах штольни (до поворота на heading)
  x1: number; z1: number       // конец
  y0: number; y1: number       // высота пола относительно входа; отличается от 0 только у входного сегмента-пандуса
  width: number                // сегменты варьируют ширину ±15% от TUNNEL_WIDTH
  isLeaf: boolean              // true — тупик или комната с бриллиантом, закрыт задней стеной
  isDiamondChamber: boolean    // true ровно у одного листа
}

interface Mine {
  x: number; z: number; y: number
  heading: number               // как сейчас: куда развёрнута локальная ось +x
  segments: MineSegment[]
  reach: number                 // максимальное расстояние от входа до любой точки графа — для isInsideMine
}
```

Генерация (внутри `placeMine`, после того как вход и `heading` найдены как
сегодня):

1. Корневой сегмент — вход-пандус: от `(0,0)` до `(x,0)` вдоль локальной +x,
   `y` уходит с `0` до `-RAMP_DROP` (1.5–2м, из RNG). Длина и уклон вместе
   дают пологий, не ступенчатый спуск.
2. Дальше идёт основной ход тем же направлением, пока не наступит первая
   развилка.
3. Всего в дереве `BRANCH_COUNT` развилок (3–4, из RNG). Каждая развилка берёт
   один из текущих открытых "листьев", ставит на его конце разветвление на
   два новых сегмента: угол каждого — угол родителя ± случайный разворот
   (в пределах, чтобы оба расходились заметно, не под 2°), длина и ширина —
   каждая из своего диапазона RNG.
4. После всех развилок в дереве `1 + BRANCH_COUNT` листьев. Один, выбранный
   RNG, становится `isDiamondChamber` — его дальний конец расширяется в
   небольшую камеру (ширина ×~1.6 на последней трети). Остальные — тупики,
   визуально и по коллизии ничем не отличаются от обычного хода, просто
   заканчиваются раньше.
5. `reach` — максимум по всем сегментам расстояния от `(0,0)` до `(x1,z1)`.

Всё дерево детерминировано одним `mulberry32(seed)` вызовом внутри
`placeMine`, как и сегодняшний выбор процедурной точки/heading — один seed,
один результат, тест на это уже есть и переживёт обобщение.

## 2. Геометрия сегмента: пол, потолок, две стены, торец

Каждый сегмент строится как набор четырёхугольников (`BufferGeometry`, не
`BoxGeometry`, потому что нужен реальный уклон и повороты, а не только
прямоугольная коробка):

- пол и потолок — по одному quad'у, вершины на `y0`/`y1` на обоих концах —
  отсюда и берётся видимый уклон пандуса и ровный пол во всех остальных
  сегментах (`y0 === y1` там);
- две стены — вертикальные quad'ы вдоль сегмента, высота `TUNNEL_HEIGHT` от
  пола до потолка на каждом конце;
- у листового сегмента добавляется торцевая стена, закрывающая тупик — то же,
  что сегодняшняя `back`, только теперь на каждом тупике, а не один раз.

Для "несимметричного, каменного" вида к вершинам каждого quad'а (кроме тех,
что на стыке с соседним сегментом — они не двигаются, чтобы стыки не
расходились) добавляется небольшое детерминированное смещение
(`mulberry32`, отдельный поток, не общий сид генерации графа, чтобы форма
хода не менялась при изменении числа развилок). Амплитуда шума жёстко меньше
зазора коллизии (см. §3), чтобь стена никогда не "утекала" внутрь прохода.

Устье (`x0=0,z0=0` конец корневого сегмента, сторона мира, а не пещеры) —
отдельная декоративная деталь: контур проёма из 6–8 точек по кругу, часть
из них сдвинута тем же детерминированным шумом дальше от центра, часть —
ближе, так что проём читается как неровная дыра в склоне, а не прямоугольная
дверь. Только визуал, коллизии там нет ни сейчас, ни после.

## 3. Коллизия

Обобщение сегодняшнего `mineObstacles`: для каждого сегмента — цепочка
маленьких кругов вдоль обеих стен (та же плотность, `WALL_CIRCLE_SPACING`),
только теперь стороны сегмента считаются от его собственного направления
(`x1-x0, z1-z0`), не от глобального `+x`. Для каждого `isLeaf`-сегмента
добавляется круг-цепочка, закрывающая его дальний конец (как сегодняшний
`back`, но на каждом тупике). Развилки не требуют отдельной коллизии —
стены двух дочерних сегментов, начинающиеся в одной точке, уже перекрывают
угол.

`localToWorld` (поворот+перенос на `m.heading` и позицию входа) не меняется —
как и сегодня, она принимает произвольную локальную точку; генератор дерева
просто считает точки не только вдоль чистой `+x`.

## 4. `isInsideMine`

Сегодняшняя проверка "на расстоянии `TUNNEL_LENGTH` от входа — уже тёмно"
обобщается на `m.reach` (посчитан в §1) плюс тот же небольшой запас, что и
сейчас, — сигнатура функции не меняется, вызывающий код (`quest/lamp.ts`,
`game/scene.ts`) ничего не замечает.

## 5. Бриллиант: где лежит

`diamondSpotInMine` находит сегмент с `isDiamondChamber === true` и ставит
бриллиант у его дальнего конца, слегка в сторону от центра — тот же приём,
что и сегодня (не по центру света, не по центру прохода). Возвращаемый тип
не меняется (`{x, y, z}`), так что `quest/placement.ts` и `main.ts` не
трогаются в этой части.

## 6. Бриллиант: форма

Заменяем `THREE.OctahedronGeometry(0.18)` (8 граней, идеально симметрично)
на `THREE.IcosahedronGeometry(0.16, 0)` (20 граней) с детерминированным
джиттером радиуса каждой вершины (`mulberry32` с фиксированным собственным
сидом — форма модели одна на всю игру, не зависит от мирового seed, это
внешний вид предмета, а не тестируемая процедурная генерация мира). Джиттер
достаточно маленький, чтобы силуэт остался узнаваемым "камнем", но заметно
неровным. Строится один раз в модуле (как сегодняшний `DIAMOND_GEO`), тест
проверяет тот же geometry-джиттер детерминирован для одного сида.

## 7. Бриллиант: свечение от лампы

Материал получает `emissive`/`emissiveIntensity`, которая считается каждый
кадр в уже существующем цикле `main.ts` (там же, где сегодня вызывается
`forest.updatePlayerLamp` и известны и позиция камеры, и состояние лампы) —
без изменений в `game/scene.ts`'s `SceneApi`. Пока лампа выключена или
бриллиант далеко — `emissiveIntensity` около нуля (тёмный камень); когда
лампа горит и игрок близко — растёт до заметного свечения. Простая функция
от `(lampOn, distance)`, без отдельного состояния квеста — если бриллиант
уже подобран, обновлять нечего (mesh снят, как и сегодня `hideQuestItem`).

## 8. Тестирование

`test/world/mine.test.ts` переписывается под граф:
- та же проверка на mapped-вход и процедурный выбор точки/heading — без
  изменений;
- новый набор: генерация с данным seed даёт дерево с ожидаемым числом листьев
  (`1 + BRANCH_COUNT`), ровно один `isDiamondChamber`, все листья кроме него
  — тупики; детерминизм (тот же seed — тот же граф, `toEqual`);
  разные seed — разный граф (хотя бы одно отличающееся поле);
- `mineObstacles`: как сегодня, плюс — обход по всем сегментам не пропускает
  ни один (число кругов растёт с числом сегментов predictable-но);
- `isInsideMine`: то же самое, но с точкой на дальнем листе — тоже "внутри";
  далеко за пределами всего графа — не внутри;
- `diamondSpotInMine`: сидит в пределах `isInsideMine`, как сегодня, плюс —
  лежит именно в сегменте с `isDiamondChamber`.

Новый тест на форму бриллианта (вероятно в `test/main` не существует — форма
живёт в `main.ts` как константа; если модуль неудобно тестировать напрямую,
джиттер-функция выносится в маленький чистый хелпер с собственным тестом на
детерминизм, как остальной процедурный код проекта требует).

`npm run silhouette-sheet` и headless-скриншот штольни (per CLAUDE.md's
"Look at it") — обязательны перед тем, как считать визуальную часть готовой:
несимметричная геометрия и джиттер — как раз то, что тесты не ловят.

## 9. Что не меняется

- Игра по-прежнему подсвечивает бриллиант только через лампу — нет отдельного
  ambient-свечения независимо от неё (см. существующий комментарий в
  `mine.ts` про то, что штольня без лампы должна быть по-настоящему тёмной).
- Один мир — одна штольня, как сегодня.
- `TUNNEL_WIDTH`/`TUNNEL_HEIGHT` остаются теми же базовыми размерами,
  сегменты лишь слегка варьируют ширину вокруг них.
